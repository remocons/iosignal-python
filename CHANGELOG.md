# Changelog

## Unreleased

- REPL keys come in three forms (`iosignal.replkey`, the same rule as the web IDE): hex of 32+ digits as before
  (the 64-digit keys keep working), a 25-symbol key `XXXXX-XXXXX-XXXXX-XXXXX-XXXXX` (Crockford base32, 125 random
  bits, case and dashes free), or a passphrase of 10+ characters (PBKDF2-HMAC-SHA256, 600000 rounds). `iosignal-repl`
  takes any of them with `-k`, `REPL_KEY`, a key file or the prompt; `tools/mpy_repl_key.py` now makes the short key.
  Boards still store the key bytes as hex in `/repl.json`, so existing boards need no change. A passphrase can be
  guessed offline by anyone who sees a session's first frame (the broker included): prefer the random key.
- Boards: a bad `/repl.json` key turns the remote REPL off instead of stopping `board.start()`.
- Devices: the command `?` only asks for the state (`apply_command`, `board.device()`): nothing changes, the state is
  sent as usual.

## 0.2.3 (2026-11-25)

- MicroPython boards: the link runs on the chip's highest hardware timer (ESP32, ESP32-S3: `Timer(3)`; ESP32-C3:
  `Timer(1)`) instead of `Timer(0)`, so code copied from tutorials, which start at `Timer(0)`, no longer stops it.
  `"timer"` in `/iosignal.json` picks another number; `board.status()` shows it. New `board.free_timer()`: a timer
  the link does not use. The button examples use it (and `Timer(1)` with an older package).

## 0.2.2 (2026-11-25)

- `iosignal.ascon` checks the native permutation (`ascon_fast`) against known answers when it is imported and uses
  it only when they match; otherwise the pure Python permutation runs (`iosignal.ascon.NATIVE` is False). A board
  whose MicroPython compiles the viper code but computes something else (a big-endian CPU, an emitter bug, changed
  type rules in a later MicroPython) then still logs in, only slower. The check costs two permutations on import.

## 0.2.1 (2026-11-25)

Speed on MicroPython boards. Same wire format and API as 0.2.0.

- `iosignal.ascon_fast`: the Ascon permutation as native code (`@micropython.viper` on 32-bit halves of each lane,
  generated by `tools/gen_ascon_fast.py`). Boards whose MicroPython has the native emitter (ESP32, ESP32-C3,
  ESP32-S3, ...) compile it on import; elsewhere (CPython, other ports) the pure Python permutation is used.
  `iosignal.ascon.NATIVE` says which one runs. Install it with the rest of the package (`mip` and the web setup page
  include it, as source).
- ESP32-C3 (MicroPython 1.29): login 142 → 3.9 ms, a 100-byte message 69 → 4.1 ms, link file frames (1400 bytes)
  637 → 24.5 ms, so file transfers through the link are no longer limited to about 2 kB/s.
- CPython: the pure Python permutation inlines its rotations (about 15 % faster than 0.2.0).

## 0.2.0 (2026-11-24)

Boho 3: login and encryption move from the old SHA-256 construction to standard Ascon (NIST SP 800-232),
the same as boho 3, IOSignal 10.0.0 (JS), IOSignal Arduino 10.0.0 and the Kotlin client.

- New `iosignal.ascon`: Ascon-AEAD128 and Ascon-CXOF128 in plain Python (CPython and MicroPython).
- `iosignal.boho`: Boho 3 packets (AUTH_REQ, AUTH_RES, ENC, ENC_E2E, ENC_PACK), `derive_key()`,
  `encrypt_session()`/`decrypt_session()` in place of `encrypt_488()`/`decrypt_488()`; `copy_key()` takes 16 bytes.
- The remote REPL (`replproto`) keys its sealer with `derive_key()`; boards and controllers must both run 0.2.0.
- Tests: Ascon known answers, a recorded JS boho 3 session and packs, the shared boho vectors.

Breaking:

- Logging in works only with IOSignal servers 10.0.0 or newer. Against a 10.0.0 server, 0.1.x can still
  connect anonymously but cannot log in; 0.2.0 cannot log in to 9.x servers.
- Keys issued for 9.x servers must be issued and registered again.
- Boards running 0.1.x cannot be updated through the link (`iosignal-repl update`) once the server is 10.0.0:
  install the 0.2.0 package over USB.
- E2E signals and REPL frames sealed by 0.1.x cannot be opened by 0.2.0, and the other way round.
